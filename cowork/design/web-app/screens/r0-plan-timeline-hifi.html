✕ Failure 1 — the percent becomes the headline

complete · 1 stage blocked
A big number reads as a computed, authoritative measure of the build. The blocked stage — the only thing the homeowner may need to act on — becomes a footnote. Never render the percent alone, never above 13 px, and never without its status word (§8.3 R2).
✓ Correct — status word first, percent subordinate
Attention needed
· 33% of stages done
The word carries the meaning; the number is texture underneath it. This is the only permitted pairing — including on an otherwise-finished plan, where Attention needed still outranks Complete (§8.3 R1·1).

This is the exact typography of the Cost pillar metric in LINA-27 — so the homeowner reads “I now owe $246,400,” which is false. Planned cost must never use .metric-val, never use the red .delta.up treatment, and never say “over budget.”

Build notes for LINA-69 — what this surface must and must not do

  • Status → token map. not_started → --idle-* (dashed circle) · in_progress → --info-* (half-filled circle) · blocked → filled --danger (triangle) · done → --ok-* (check circle). --info-* and --idle-* are the only two new token groups; everything else is inherited from LINA-27. Amber (--warn-*) stays reserved for change order pending — do not reuse it for a stage.
  • Blocked carries five signals, not one hue (AC-P7): filled chip + label + triangle icon + 5 px left rail + tinted card, plus the inline reason quote, the plan-level headline, the red health dot in the switcher, and a count badge on the desktop Plan nav item. Removing any one of these must still leave blocked unmistakable in greyscale.
  • Percent rules. Render only when status === 'in_progress'; max 13 px; always muted; always preceded by · and the status word; never in a heading element. In the report form, the percent field is disabled and captioned, not removed. Reporting done drops percent from the headline entirely (§5).
  • Plan headline. Compute per §8.3 R1 in exact order; the percent string is always suffixed to the word and never rendered on its own. Zero stages ⇒ no headline node at all — render the empty state instead. Do not emit “0%”, and keep the project health dot neutral.
  • Allocation vs budget. Stage cost uses the .alloc label pattern (“Planned allocation $X”), never a bare currency figure. The plan-level hint uses .allocbar — dashed border, --sunken ground, “information only” eyebrow, and a link out to the Cost pillar. Over-allocation is neutral text, not red, and never uses the word “over budget”.
  • Roles. Homeowner: identical read layout with zero authoring controls rendered, plus the .readonly pill so the absence is explained rather than mysterious. GC: same components + drag handle, Report progress / Edit / Add stage / Plan doc, all in Builder Orange. A homeowner write attempt is an authorization denial surfaced as a denial (§8.2, LINA-56 finding — never a 500).
  • No acknowledge, no comment box anywhere on this surface (§2 Q3). The response path is the .respond card — present on the plan, in the stage history, and in the desktop drawer — routing to Log a decision or Raise a change order in one tap.
  • Out of scope, visually enforced (§7): no bars-across-time, no dependency lines, no critical path, no “N days late”, no photo attachments. Dates render as plain planned ranges; a stage past its planned start while not_started renders unchanged and un-annotated (AC-P13).

Open questions back to the PM (LINA-43) — none are blockers

  • “Happening now” label. §8.3 R3 defines a current-stage pointer but doesn’t name it in the UI. I’ve used Happening now rather than “Current stage” because it is plainer for a non-technical homeowner. Confirm the wording, or give me yours.
  • Blocked recency. The headline names the blocked stage and its report date. If two stages are blocked at once, I show the first in plan order (consistent with R3) and a “+1 more” affordance. Flagging in case you want most-recent instead.
  • Notification wording. The empty state promises “we’ll notify you the moment the plan lands”, and blocked is the natural push candidate. Notifications aren’t in the R0 spec — if there is no notification channel in R0, I’ll drop that line rather than promise it.
